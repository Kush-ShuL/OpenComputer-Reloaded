# Hologram projectors

Both projector tiers follow MightyPirates/OpenComputers commit `258943363ea8fc4ef14948e6bc6f67375061580c`: `common/tileentity/Hologram.scala`, `common/block/Hologram.scala`, the `Rotatable`, `RotatableTile`, `Environment` and `Tickable` traits, the common block item, and `client/renderer/tileentity/HologramRenderer{,Fallback}.scala`. The original assets and attribution remain in place. The original family has no separate hologram item/block driver: its world block is the component host.

The component retains a 48×32×48 volume stored as two 48×48 integer bitplanes. Lua coordinates and palette indices start at one. Tier one has one palette entry; tier two has three and additionally supports base rotation and rotation speed. Boolean voxel values, clamped vertical fills, partial raw input in x/z/y order, the original inclusive/clamped column-copy endpoints and overlap direction, and the original callback descriptions are preserved. Copies retain the original area-based pause calculation, and raw writes retain the configured delay.

`getPaletteColor` uses RGB. As in the pinned source, `setPaletteColor` returns the previous value in the renderer's BGR byte order. The modern renderer stores RGB internally, so the callback explicitly converts that return value. Scale, translation and rotation use the original floating-point argument/clamp behavior. Rotation arguments are all checked before committing a change.

Power consumption counts nonzero column bitplanes, rather than individual lit voxels, and multiplies that ratio by scale, the configured cost and power tick frequency. Empty projections therefore become powered at zero cost even on an empty network. The projector connects only through its local bottom. Original placement constrains pitch to horizontal and inverts the player's yaw; the scrench rotates it about the vertical axis. The half-height block, tier rarity, original tooltip, book-enchantment exclusion and creature-spawn exclusion are retained.

World saves use the existing shared `SaveHandler`: voxel bitplanes and RGB palette entries go to the node address's `_data` auxiliary snapshot, while node identity, tier, scale, translation and rotations remain in the block state tag. Loading also accepts the earlier inline volume/palette representation. Client synchronization uses full inline snapshots and revisioned deltas; it does not schedule auxiliary saves. Power is synchronized to clients rather than persisted as server state.

The existing renderer was compared against the pinned source and retains its six face windings/UVs, hidden-face removal, five-second GPU cache lifetime, depth pre-pass followed by additive equal-depth color pass, 0.75 opacity with distance fading, pitch/yaw then base rotation then world-time rotation, projection translation/scale, and configured Gaussian flicker. Its modern frustum bounds conservatively include arbitrary projection rotations. Existing ordered snapshot/delta retry handling and dedicated-server client-class isolation remain in use.

`HologramContract` provides finite dedicated-server checks using real placed projectors and their actual Case machine contexts. It covers both tiers' voxel/copy/raw/palette/transform operations, errors, registry-aware auxiliary save/load and actual periodic energy transitions. It does not claim to measure callback pause duration on stopped machines or accept client rendering.

A finite Windows visual check uses the same asymmetric projection on both tiers: show separated red/green/blue columns on tier two and a single-color outline on tier one; verify top/bottom scrench rotation, scale/offset and tier-two base/world-time rotation; view it from outside and inside at near/fading distances; then leave/re-enter its chunk and reload resources. This checks the existing depth/additive render, transforms, palette and snapshot/cache behavior without a broader device matrix.

Windows NeoForge 21.1.224 run `advanced-20261027-e2` passed both real projector tiers' placement, physical connectivity, callbacks, error ordering, auxiliary save/mutate/load and actual periodic energy transitions. The report is `build/api-compat-addon/devices/advanced-20261027-e2/device-results.txt`. The visual scene above remains part of shared C20; the server result does not claim client-render acceptance.
