# Recipe and vanilla-platform behavior

The source of behavior is MightyPirates/OpenComputers commit `258943363ea8fc4ef14948e6bc6f67375061580c`: `common/recipe/{Recipes,ExtendedRecipe,ContainerItemAwareRecipe}.scala`, the extended shaped/shapeless recipes, `util/ItemUtils.scala`, `common/template/DisassemblerTemplates.scala`, and `integration/minecraft` drivers, converters, events and recipe handler. Existing resources, licenses and attribution remain retained.

## Recipe processors and material returns

The pinned source registers exactly three HOCON recipe handlers, all from the Minecraft integration: `shaped`, `shapeless` and `furnace`. These are now registered by that integration after its blacklist check, rather than unconditionally in a static initializer. An independent higher-priority data-pack recipe remains independent of these handlers. Output counts at or below zero do not register a configured recipe.

The bundled `gregtech.recipes` file documents twelve `gt_*` names and fluid/count/energy/time fields, but the pinned source does not implement or register these machine handlers. Its public `Recipes.parseFluidIngredient` helper likewise has no caller. The port retains the original profile and adapts that helper to named modern fluids with the original default amount of 1000; this is not a GregTech machine integration. No machine bridge or fluid material-return behavior is invented to satisfy obsolete profile comments.

Every configured shaped/shapeless recipe now applies the original `ExtendedRecipe` data rules, including generic recipes. Previously only a short list of result names received a transform. The rules retain default processor architecture, the last actual map in navigation crafting, server-created linked-card channels, floppy formatting/copying, two-EEPROM copying with node address removal, print light/beacon edits, and assembled-device EEPROM replacement. BIOS and program-disk factories preserve the configured output count. Formatting omits the original default light-gray floppy color while preserving other explicit colors; copying merges missing original custom-data keys into the recipe's output. Modern assembled-device slot identities and unrelated hardware remain preserved during EEPROM replacement.

The original default profile contains both `luabios` and an obsolete `luaBios` section. The pinned registry used the exact registered name, whereas normalizing every root key to a recipe ID allowed the obsolete section to overwrite a configured `luabios` during reload. Exact lowercase keys now take priority over colliding legacy spellings, including boolean visibility settings; the original resource sections remain intact.

Crafting remainders still come from the real base recipe's normal item-container processing. Disassembly continues to read real crafting ingredients, omit returned buckets, apply the configured material blacklist, divide by recipe output count, and split recovered material into individual queue entries. The existing manufacturing-recipe search skips self-recrafting candidates before continuing; it is retained because the already verified navigation recipe otherwise masked the real manufacturing recipe. Existing template-provided stochastic materials and guaranteed drops are unchanged. This batch does not rerun the closed assembler/disassembler family.

## Vanilla drivers

Furnace item environment discovery now accompanies the existing real furnace driver, including the port's smoker/blast-furnace subclasses. Its five callbacks retain the original names, timing fields and documentation and read the captured actual block entity.

Beacon, brewing stand, comparator, mob spawner, note block, jukebox and command-block callbacks do not invent inventory-style right-click authorization checks. The original inventory driver does have that protection path, which is retained: actual interaction cancellation, explicit deny and an unusable inventory refuse access. The pinned Java `DriverInventory.notPermitted` contains an erroneous inverted Boolean predicate; retaining the port's correct refusal behavior is an explicit bug correction, not a claim that the pinned predicate was equivalent.

The modern note-block driver reads the actual `NOTE` property for its original direct pitch callback instead of a tick-delayed cache. Pitch remains one-based, restricted to 1–25. Triggering requires air immediately above the note block, matching the pinned behavior rather than accepting the modern skull-instrument exception. Its explicit driver matching also honors the Minecraft integration blacklist. Command execution still requires the original enable-driver setting and the server's command-block switch, retains its 0.1-second pause, and returns the real success count and last output.
